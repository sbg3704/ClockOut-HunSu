# 성능과 안전 (초안 v0, 2026-11-11)

훈수꾼은 **엑셀 위에서 도는 보조 프로그램**이다. 엑셀이 느려지거나 멈추거나 데이터를 잃게 하면 가치가 없다. 사용자 우선순위는 반응성이 첫째, 예쁨이 둘째다. 아래 기준을 못 지키면 기능을 줄이거나 설계를 고친다.

## 1. 성능 예산
| 항목 | 목표 | 재는 법 |
|---|---|---|
| 선택 변경 → 화면 반영(짧은 값) | 50ms 이내 | 신호 보낸 시각부터 첫 그림까지(5장) |
| 패널 열기 | 100ms 이내 | 입력 시각부터 마지막 프레임까지 |
| 애니메이션 | 60fps, 프레임 건너뜀 없음 | 프레임 시간 기록 |
| 다리가 엑셀에서 쓰는 시간(이벤트 한 번) | 5ms 이내 | 엑셀 안 타이머 |
| `light` 조회 | 20ms 이내 | 틀 쪽 왕복 |
| `normal` 조회 | 100ms 이내(1만 셀 시트) | 같음 |
| `heavy` 조회 | 사용자가 기다림을 느끼기 전 시작 표시, 1초 이내 첫 결과 | 같음 |
| 엑셀 창 이동 중 오버레이 어긋남 | 한 프레임 이내 | 이동 중 위치 기록 비교 |
| 상시 메모리 | 300MB 이내(반응성과 화려함이 우선) | 작업 관리자 값 |
| 상시 CPU(아무 일 없을 때) | 1% 이내 | 같음 |

- **재는 구간을 나눈다**(2026-11-12): 신호(엑셀 이벤트→틀 도착), 조회(왕복), 그리기(데이터 도착→첫 그림), 입력(누름→반응 시작), 장시간(8시간 켜 둔 메모리·CPU). "선택→화면 50ms"는 신호+`light` 조회+그리기의 합이다.
- 목표는 평균이 아니라 **P95**(100번 중 95번)로 판정하고 최댓값도 함께 적는다. 0단계 실측으로 목표 숫자를 한 번 고쳐 확정한다.

### 0단계 확인 결과 (2026-11-12, 사무실 PC: 논리 CPU 24, Windows 11 26200, 엑셀 16.0 64비트, .NET 10.0.15, 배율 100%)
`tools/bench/run_bench.ps1`(Release, 보이지 않는 엑셀, 선택 100번, 창 이동 200번, 패널 30번). 아래는 마지막 실행 값이고, 괄호는 같은 날 4번 실행의 P95 범위다.

| 항목 | 목표 | 평균 | P95 | 최대 | 판정 |
|---|---|---|---|---|---|
| 선택 → 화면 합계 | 50ms | 8.3 | 10.3 (10.3~38.0) | 24.7 | 통과 |
| ㄴ 신호(엑셀 이벤트→앱 도착) | — | 4.3 | 6.3 (6.3~20.8) | 7.8 | |
| ㄴ `light` 조회 왕복 | 20ms | 2.8 | 4.5 (4.5~13.0) | 19.6 | 통과 |
| ㄴ 그리기(결과→다음 프레임) | — | 1.2 | 1.8 | 2.5 | |
| 다리 이벤트 처리(엑셀 안) | 5ms | 0.05 | 0.07 | 0.11 (모든 실행 최대 0.9) | 통과 |
| 패널 열기: 첫 프레임 | 100ms | 1.0 | 2.0 | 10.6 | 통과 |
| 패널 열기: 마지막 프레임 | 100ms | 158 | 162 | 165 | **넘음 — 문서끼리 충돌**(아래) |
| 창 이동 → 오버레이 제자리 | 한 프레임(16.7ms) | 8.0 | 10.6 (10.6~27.0) | 36.7 | 통과(첫 실행만 넘음) |
| ㄴ 창 이벤트 도착 | — | 7.3 | 9.8 | 16.5 | |
| ㄴ 앱의 SetWindowPos | — | 7.2 | 8.5 | 10.4 | |

- **패널 열기 목표가 디자인 기준과 맞지 않는다.** `docs/03`은 패널 열고 닫기를 `base` 200ms 움직임으로 정했는데, 이 표는 "입력부터 마지막 프레임까지 100ms"다. 둘 다 지킬 수 없다. 반응(첫 프레임)은 2ms라 체감 문제는 없다. **사용자 결정(2026-11-12)**: 목표(마지막 프레임 100ms)는 그대로 두고 패널 움직임을 `fast` 120ms로 줄인다(`docs/03` 6장). 위 158~165ms는 200ms 움직임 때 값이므로 PC에서 다시 잰다.
- 창 따라가기는 첫 실행에서 P95 27ms로 한 번 넘었고 이후 세 번은 10.6~14.3ms였다. 최대값은 매번 35~48ms가 한두 번 있다(백그라운드 작업 추정). SetWindowPos 자체가 7~9ms 걸리는 것은 WPF 투명 창(레이어드 창) 다시 그리기 비용으로 보이며, 1단계에서 `SWP_NOREDRAW`/`SWP_NOCOPYBITS` 등을 시험해 줄일 여지가 있다.
- 시험 창은 측정 도구가 만든 창이다(엑셀을 보이게 띄우지 않는 규칙). 실제 보이는 엑셀을 손으로 끌 때(모달 이동 루프)의 어긋남은 사용자가 눈으로 확인한다(HANDOFF).
- 상시 메모리·CPU와 8시간 장시간, 모니터 배율 150/200%, 모니터 두 대는 0단계에서 재지 않았다(1단계에서).

## 2. 갱신 무게와 한도
구조와 규칙 6.3장의 `weight`를 틀이 이렇게 집행한다.
| 무게 | 조회 시점 | 한도 |
|---|---|---|
| `light` | 신호 뒤 즉시(같은 신호는 묶음) | 응답 8KB |
| `normal` | 입력이 0.5초 멈춘 뒤, 보이는 모듈만 | 응답 64KB, 행 200 |
| `heavy` | 사용자가 열거나 새로 고침을 눌렀을 때만 | 응답 256KB, 노드 500, 깊이 8 |

- 보이지 않는 모듈(접힘, 숨김)은 `tab`과 `chip`에 필요한 숫자만 받는다.
- 엑셀이 바쁘면(`excel_busy`) 조회를 미루고 마지막 내용을 흐리게 둔다. 세 번 연속 거절되면 다음 신호까지 쉰다.
- 한 번에 진행 중인 조회는 엑셀 인스턴스당 하나다. 새 신호가 오면 앞선 대기 조회는 취소한다.

## 3. 엑셀을 보호하는 규칙 (다리)
1. 이벤트 처리기는 신호를 보내고 즉시 끝낸다(5ms). 셀을 읽거나 계산하지 않는다.
2. 엑셀 설정(`ScreenUpdating`, `Calculation`, `EnableEvents`, `Interactive`)을 바꾸지 않는다. 바꿔야 하는 조회가 생기면 설계를 다시 한다.
3. 셀 값, 서식, 수식을 쓰지 않는다. 이동 명령 외에는 선택과 활성 시트를 바꾸지 않는다.
4. 큰 범위는 셀 하나씩 읽지 않고 한 번에 배열로 읽는다(`Range.Value2`, `SpecialCells`).
5. 조회가 한도를 넘으면 `truncated`로 자르고 계속하지 않는다.
6. 보호된 보기, 읽기 전용, 다른 이름으로 저장 중 같은 상태에서는 조용히 쉰다.
7. 어떤 오류도 사용자 화면의 오류 창으로 나오지 않는다.

## 4. 화면을 빠르게 지키는 규칙 (틀)
- 엑셀 호출은 전용 작업 스레드에서만 한다. 화면 스레드는 엑셀을 기다리지 않는다.
- 효과가 느려지면 자동으로 낮춘다: 최근 30프레임 중 5프레임 이상이 16.7ms를 넘으면 흐림 배경을 끄고, 그래도 느리면 효과를 `보통`으로 낮춘다(설정에는 "자동으로 낮춰짐"이라고 알린다).
- 순서도 배치와 정렬은 별도 스레드, 결과는 캐시한다.
- 숨은 상태(엑셀이 앞에 없을 때)에서는 그리기를 멈추고 그림 캐시만 줄인다.
- 시작은 `ReadyToRun`과 숨은 준비로 처음 나타날 때 로딩을 보지 않게 한다.

## 5. 측정 방법
- **사용자 PC에서 키보드, 마우스, 화면 조작을 하지 않는다.** 측정은 COM으로 엑셀 선택을 옮기고 시각을 기록하는 스크립트로 한다.
- `tools/bench/`에 측정 도구를 둔다: 선택을 N번 옮기며 `신호 시각 → 첫 프레임 시각`을 기록하고 평균, 95%, 최대를 출력한다. 엑셀은 보이지 않는 인스턴스를 쓴다.
- 시험 통은 크기별 시트(1천, 1만, 10만 셀, 수식 1천 개, 오류 100개, 참조 깊이 8)를 만들어 쓴다.
- 결과는 PR 본문에 표로 붙인다. 목표를 넘으면 숫자와 원인 추정을 같이 적는다.

## 6. 실패했을 때 (복구 표)
| 상황 | 훈수꾼의 동작 | 코드 |
|---|---|---|
| 엑셀 없음 | 숨고 기다림 | `excel_missing` |
| 엑셀이 편집 중 | 마지막 내용을 흐리게, 곧 다시 시도 | `excel_busy` |
| 다리 없음, 꺼짐 | 칼퇴에서 켜도록 안내, 나머지는 그대로 | `bridge_missing` |
| 다리 판이 낮음 | 업데이트 안내 | `bridge_old` |
| 조회 실패 | 그 모듈만 "불러오지 못함", 다시 시도 단추 | `query_failed` |
| 모듈 선언 오류 | 그 모듈만 건너뜀, 작업 기록 | `manifest_bad` |
| 틀이 멈춤(응답 없음) | 칼퇴가 다시 시작(10분에 3번까지), 넘으면 끄고 알림 | — |
| 저장 실패(배치, 설정) | 메모리에만 두고 다음에 다시 저장 | `store_failed` |
| 화면 그리기 실패(그래픽 오류) | 소프트웨어 그리기로 낮춰 다시 시작 | — |

- 어떤 실패도 엑셀이나 칼퇴 매니저를 멈추게 하지 않는다.
- 문제가 반복되면 설정의 "훈수꾼 끄기"로 한 번에 쉬게 한다(`Ctrl+Alt+Shift+H`와 같은 효과).

## 7. 개인정보와 회사 자료
- **엑셀 안의 값은 회사 자료일 수 있다.** 셀 값, 수식, 시트 이름, 파일 경로는 메모리에서만 쓰고 파일, 작업 기록, 오류 보고에 남기지 않는다. 기록에는 코드, 주소 모양, 개수 같은 값 없는 정보만 적는다.
- 훈수꾼은 네트워크로 엑셀 내용을 보내지 않는다. 훈수꾼 자체는 인터넷 연결 코드를 갖지 않고, 판 확인과 받기는 칼퇴가 한다.
- 화면 공유와 발표를 위해 `Ctrl+Alt+Shift+H`(전부 숨김)가 항상 즉시 작동한다.
- 캡처 방지는 하지 않는다(사용자 PC 화면 자료이므로 사용자 몫).

## 8. 모듈과 배포물의 안전
- 모듈은 코드를 실행하지 않는 JSON 선언뿐이다. 선언은 형식 검사(스키마), 표현식 한도(데이터 연결과 조건 한 줄), 크기 한도(64KB)를 통과해야 한다.
- 모듈이 쓸 수 있는 명령은 선언에 적은 것뿐이고, 읽는 범위도 선언의 `scope`까지다. 틀은 그 밖을 막는다.
- zip을 풀 때 경로 탈출(`..`, 절대 경로), 풀린 크기와 파일 수 한도를 검사한다(칼퇴 Core의 검사 재사용).
- 배포물은 칼퇴 추가기능과 같은 안전 규칙을 쓴다: 카탈로그에 SHA-256, https와 허용된 저장소에서만 받기, 임시 이름에 받아 해시 확인 뒤 교체, 실패하면 이전 판으로 되돌리기, 작업 기록.
- 받아 온 오픈소스는 판을 고정하고 `SOURCES.md`에 출처, 판, 라이선스, 받은 날짜, 쓰는 곳을 적는다. GPL 계열과 상용 겸용은 쓰지 않는다. 판을 올릴 때는 전체 시험을 다시 돈다.
- 서명이 없는 배포이므로 SmartScreen 경고가 날 수 있다는 안내를 소개 화면에 둔다(칼퇴와 같다).
